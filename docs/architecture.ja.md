# アーキテクチャ

## 概要

```text
Market Data（全期間を毎回再取得）
    │
    ▼
Daily Scheduler
    │
    ▼
Drawdown Engine（state_machine.run を最初から再実行）
    │
    ├── 52週高値
    ├── 基準高値（ロック）
    ├── ドローダウン / Level 判定
    ├── Recovery の確定 / 取り消し
    └── 底打ち後の上昇の追跡（保有継続 / 売りライン）
    │
    ▼
通知済みイベントとの差分
    │
    ▼
Notification
```

米国市場の終了後に1日1回実行します。目指すのは低遅延ではなく、低コストで
ほぼメンテナンス不要のまま何年も動き続けることです。

## モジュール（`src/`）

- `market_data.py` — 銘柄の日次終値を取得する。
- `drawdown.py` — ドローダウンの純粋な計算（52週高値、基準高値、ドローダウン%）。
  I/Oなし。
- `state_machine.py` — NORMAL ⇄ DRAWDOWN の状態遷移（DRAWDOWN_MODE_ENTER /
  LEVEL_TRIGGER / RECOVERY_CONFIRMED / RECOVERY_UNDERCUT / RENEWED_DECLINE /
  NORMAL_RESUME）を、価格系列の全期間に対して再実行する。独立した「RECOVERY」
  モードはなく、Recoveryの確定・取り消しはDRAWDOWN内のサブ状態として扱う
  （docs/strategy.ja.md を参照）。それとは別に、`track_uptrend`が各底打ち後の
  反発を、これらのモードとは独立に追跡する（UPTREND_ARMED / UPTREND_EXIT）。
  持つ価値のある上昇は、NORMAL_RESUMEをはるかに超えて続くため。
- `main.py` — 本番の日次ランナー。最新の価格を取得し、state machineを実行し、
  `notification_state.py`と差分を取って、新しいイベントだけをメール通知する
  （後述の「ステートレスと株式分割」「保存する状態」を参照）。
- `notification_state.py` — どのイベントをすでに通知したかを、日をまたいで
  追跡する（後述の「保存する状態」を参照）。
- `status.py` — Heartbeatに載せる、銘柄ごとの「今の段階」の要約を、その日の
  イベントと価格系列から導出する。
- `event_format.py` — イベント1件を人間が読める形式にする、`backtest.py`
  （表示用）と`notifier.py`（メール本文用）で共有する整形処理。
- `notifier.py` — 新しいイベントごとの通知と、エラー通知・定期的なHeartbeatを、
  メール（SMTP。`.env.example`を参照）で送る。
- `config.py` — `config/*.yaml`を`TickerConfig`に読み込む。`backtest.py`と
  `main.py`で共有する。
- `backtest.py` — 設定した各銘柄の全期間の価格に対してstate machineを実行し、
  発生したはずのイベントをすべて表示する。
- `threshold_sweep.py` — 調整用の補助ツール。`watch_threshold`の候補を順に試して
  過去にDrawdown Modeが何回発生したかを示し、指定した閾値でのRecoveryの経過を
  表示する。銘柄ごとの値の調整に使う（docs/strategy.ja.md を参照）。
- `exit_sweep.py` — 上昇の売り条件を調整するための補助ツール。底打ちから売るまでの
  1往復ごとの成績を、`trail_from_peak`の候補ごとに掛け合わせて比べる。比較用に
  「2倍で売る」「売らない」も並べて表示する。
- `synthetic.py` — 原指数からレバレッジETFの長期の合成系列を作る（レバレッジ、
  借入コスト、経費率を反映）。調整用のツールに`--synthetic`を付けると、ETF自体が
  存在しなかった数十年分も含めて検証できる。

バックテストと本番の監視は、まったく同じ`state_machine.run`を呼び出します。
違うのはデータの取得元と、得られたイベントの扱い（表示するか通知するか）だけです。
これはたまたまではなく、設計上欠かせない点です（後述の「ステートレスと株式分割」を
参照）。バックテストで決めたことを本番でも信頼できるのは、このためです。

## ステートレスと株式分割

`state_machine.run`は（全期間の価格履歴、設定）だけで決まる純粋な関数で、呼び出しの
間で何も記憶しません。本番では、途中の`reference_high`や`mode`を日をまたいで保存する
のではなく、毎日その銘柄の*全期間*の価格履歴に対して最初から再実行します。

これは単に簡単だからではなく、意図的な設計です。レバレッジETFは、通常の
インデックスファンドよりはるかに頻繁に株式分割・併合を行います（SOXLとTECLは
どちらも2021年に実施）。価格履歴のAPIはどれも、分割があると過去の価格を後から
調整します。そのため、分割前の昨日に保存した`reference_high`は今日には黙って
間違った値になり、分割後の終値と比べたときに偽のドローダウンが発生します。毎回
新しく取得した（正しく調整された）系列から計算し直せば、この問題はまるごと
回避できます。古くなるような保存済みのロック値が、そもそも存在しないからです。
日次データは1銘柄あたり約4,500行なので、全期間を再実行しても実質的なコストは
かかりません。

終値が欠けている行は、再実行の前に除外します（`load_close`）。NaNの終値はどの
閾値と比べても偽になるため、エラーにならずにその日の判定を黙って飛ばしてしまいます。
取引時間中に取得したデータは、まさにこうした未確定の行で終わっていることがあります。

## 保存する状態（銘柄ごと）

保存が必要なのは「すでに何を通知したか」だけです（`src/notification_state.py`）。
これまでに見たイベントの件数を単純に数える方式（`events_notified_count`で、
`events[count:]`を新規とみなす）は手軽ですが壊れやすいため採用していません。
銘柄の設定を変えたり、データ取得元が履歴を修正・延長したりすると、`run()`の
出力の並びが変わり、件数が黙ってずれます。何年も放置して動かすシステムで、黙って
起きてはいけない種類の壊れ方です。代わりに、「通知済み」を内容に基づくキー
`(日付, イベント種別, detail)`で管理します。`detail`は`LEVEL_TRIGGER`なら
level（1日の急落で複数のlevelを一度に割り込むことがあるため）、`UPTREND_EXIT`なら
reason、それ以外はNoneです。通知の候補にするのは直近45日のイベントだけで、
保存済みのキー集合も保存のたびに同じ期間に刈り込みます。こうすれば、それより前の
履歴で並びが変わっても古い通知が復活・重複しませんし、状態ファイルが際限なく
増え続けることもありません。

```text
ticker
notified_event_keys    # {(date, event_type, detail), ...}。直近45日に刈り込み済み
last_updated
```

いずれにしても、それ以外（mode、ロックした基準高値、最安値、確定した安値など）は
その日の`run()`の中にだけ存在し、価格履歴と設定から毎回計算し直すもので、
保存はしません。唯一の例外はHeartbeatの「今の段階」の要約（`src/status.py`）で、
state machine内部のループ変数をそのまま公開するのではなく、`run()`が返した
イベント一覧と価格系列から事後的にmode・ドローダウン%・上昇の天井などを
導出し直しています。

このモジュールのconfig/stateは、ただのファイルパス（`--config`、`--state`）として
渡します。そのパスの実体（今はローカルファイル、デプロイ後はS3やSSMかもしれない）
をどこに置くかはPhase 4（デプロイ）側の決定であり、この差分ロジックとは
切り離しています。

## 設定

監視ロジックと銘柄ごとのルールは分離しています。銘柄を追加するのにコードの変更は
不要です。形式は[config/config.example.yaml](../config/config.example.yaml)を参照
してください（値は例示用です）。実際の設定はこのリポジトリの外に置き、`--config`で
渡す想定です。

## 通知

メール（SMTP。`.env.example`と`notifier.py`を参照）で送ります。
`state_machine.run`から出た新しいイベントごとに1件通知し、加えて次を送ります。

- エラー（データ取得・ジョブの失敗。取得データが止まっている・欠けている場合も含む。
  `main.py`は、ある銘柄の最新終値が`STALE_AFTER_DAYS`より古い場合や、行数が前回から
  大きく減った場合は、そのまま計算せずにエラー扱いにする）。
- Heartbeat（毎回の実行で送る — 今のところ「静かな日」と「通知がある日」を区別する
  仕組みがないため、実質的に毎日になる。システムが動いていることを確認する役割で、
  普段は長期間何も通知しないのが正常なので、障害に何年も気づかないことを防ぐ主な
  手段になる）。あわせて、各銘柄の今の段階を、最新終値の基準日付とともに具体的な
  数字で示す。Drawdown Mode中なら、どこまで下がっているかと次のLevel。上昇の追跡中
  なら、2倍まで持つ段階か売りラインの段階か、天井とその日付、天井からの現在の下落率、
  売りラインの価格。利用者はめったに相場を見ないので、「何をすればいいんだっけ？」に
  最新の通知だけで答えられる必要がある。毎日のHeartbeatが頻度として多すぎるか、
  頻度を設定可能にすべきかは未決定。スケジューラ側（Phase 4）からでも頻度を
  制御できるため、そちらが決まってから検討する。

銘柄を初めて扱う日（またはstateファイルを失って復旧した直後）は、通知の窓内に
入っているイベントをいきなり通知するのではなく、「既知のもの」として記録だけする
（`src/notification_state.py`、`src/main.py`の`process_ticker`を参照）。どれも
「今日起きたこと」ではないため。

## デプロイ

1日1回、**米国市場の引けから十分に時間を置いて**動くクラウドのスケジューラ
（Phase 3時点では未決定 — 例: AWS EventBridge + Lambda、またはprivateリポジトリ
でのGitHub Actionsの定期実行など）。この余裕時間は省略できません。取引時間中は
yfinanceがNaNではない未確定の当日値を返すことがあり、「ステートレスと株式分割」
の`dropna()`はこれを防げません。未確定値で計算したイベントは通知・送信済みとして
記録されてしまい、後で本当の終値が出ても取り消せません。

秘密情報（SMTP認証情報、APIキー）は環境変数やシークレットマネージャー経由で渡し、
コミットはしません。[.env.example](../.env.example)を参照してください。
秘密情報以外にも、デプロイ先によって次の2点が決まります。

- `main.py`の`--config`/`--state`の実体（ローカルファイル、S3、SSMなど）。
- `market_data.py`の価格キャッシュ（`data/`）をどこから書き込めるか。毎回の
  refreshで書き込むため、読み取り専用のランタイム（Lambdaのデプロイパッケージ
  など）ではそのままでは書き込めない。`DATA_DIR`を（例えばLambdaなら提供される
  が永続化はされない`/tmp`などへ）設定変更できるようにする必要があり、現状の
  リポジトリ相対の固定パスのままでは対応できない。
