# アーキテクチャ

## 概要

```text
Market Data（全期間を毎回再取得）
    │
    ▼
Daily Scheduler
    │
    ▼
Drawdown Engine（state_machine.run を最初から再実行）
    │
    ├── 52週高値
    ├── 基準高値（ロック）
    ├── ドローダウン / Level 判定
    └── Recovery の確定 / 取り消し
    │
    ▼
通知済みイベントとの差分
    │
    ▼
Notification
```

米国市場の終了後に1日1回実行します。目指すのは低遅延ではなく、低コストで
ほぼメンテナンス不要のまま何年も動き続けることです。

## モジュール（`src/`）

- `market_data.py` — 銘柄の日次終値を取得する。
- `drawdown.py` — ドローダウンの純粋な計算（52週高値、基準高値、ドローダウン%）。
  I/Oなし。
- `state_machine.py` — NORMAL ⇄ DRAWDOWN の状態遷移（DRAWDOWN_MODE_ENTER /
  LEVEL_TRIGGER / RECOVERY_CONFIRMED / RECOVERY_UNDERCUT / RENEWED_DECLINE /
  NORMAL_RESUME）を、価格系列の全期間に対して再実行する。独立した「RECOVERY」
  モードはなく、Recoveryの確定・取り消しはDRAWDOWN内のサブ状態として扱う
  （docs/strategy.ja.md を参照）。
- `notifier.py` — 新しいイベントごとの通知と、エラー通知・定期的なHeartbeatを送る。
- `backtest.py` — 設定した各銘柄の全期間の価格に対してstate machineを実行し、
  発生したはずのイベントをすべて表示する。
- `threshold_sweep.py` — 調整用の補助ツール。`watch_threshold`の候補を順に試して
  過去にDrawdown Modeが何回発生したかを示し、指定した閾値でのRecoveryの経過を
  表示する。銘柄ごとの値の調整に使う（docs/strategy.ja.md を参照）。

バックテストと本番の監視は、まったく同じ`state_machine.run`を呼び出します。
違うのはデータの取得元と、得られたイベントの扱い（表示するか通知するか）だけです。
これはたまたまではなく、設計上欠かせない点です（後述の「ステートレスと株式分割」を
参照）。バックテストで決めたことを本番でも信頼できるのは、このためです。

## ステートレスと株式分割

`state_machine.run`は（全期間の価格履歴、設定）だけで決まる純粋な関数で、呼び出しの
間で何も記憶しません。本番では、途中の`reference_high`や`mode`を日をまたいで保存する
のではなく、毎日その銘柄の*全期間*の価格履歴に対して最初から再実行します。

これは単に簡単だからではなく、意図的な設計です。レバレッジETFは、通常の
インデックスファンドよりはるかに頻繁に株式分割・併合を行います（SOXLとTECLは
どちらも2021年に実施）。価格履歴のAPIはどれも、分割があると過去の価格を後から
調整します。そのため、分割前の昨日に保存した`reference_high`は今日には黙って
間違った値になり、分割後の終値と比べたときに偽のドローダウンが発生します。毎回
新しく取得した（正しく調整された）系列から計算し直せば、この問題はまるごと
回避できます。古くなるような保存済みのロック値が、そもそも存在しないからです。
日次データは1銘柄あたり約4,500行なので、全期間を再実行しても実質的なコストは
かかりません。

## 保存する状態（銘柄ごと）

保存が必要なのは「すでに何を通知したか」だけです。**Phase 3の最初に決める設計
事項**として、これまでに見たイベントの件数を単純に数える方式
（`events_notified_count`で、`events[count:]`を新規とみなす）は手軽ですが壊れやすい
です。銘柄の設定を変えたり、データ取得元が履歴を修正・延長したりすると、`run()`の
出力の並びが変わり、件数が黙ってずれます。何年も放置して動かすシステムで、黙って
起きてはいけない種類の壊れ方です。実装前に決めておくべき、より安全な形は次の
とおりです。「通知済み」を内容に基づくキー（例: `(日付, イベント種別, levelまたは
閾値)`）で管理し、通知の候補にするのは直近（例えば30日）のイベントだけにする。
こうすれば、それより前の履歴で並びが変わっても、古い通知が復活したり重複したり
しません。

```text
ticker
notified_event_keys    # 例: {(date, event_type, level), ...}。直近の期間のみ
last_updated
```

いずれにしても、それ以外（mode、ロックした基準高値、最安値、確定した安値など）は
その日の`run()`の中にだけ存在し、価格履歴と設定から毎回計算し直すもので、
保存はしません。

## 設定

監視ロジックと銘柄ごとのルールは分離しています。銘柄を追加するのにコードの変更は
不要です。形式は[config/config.example.yaml](../config/config.example.yaml)を参照
してください（値は例示用です）。実際の設定はこのリポジトリの外に置き、`--config`で
渡す想定です。

## 通知

`state_machine.run`から出た新しいイベントごとに1件通知し、加えて次を送ります。

- エラー（データ取得・ジョブの失敗）
- Heartbeat（定期的に送り、システムが動いていることを確認する。普段は長期間
  何も通知しないのが正常なので、障害に何年も気づかないことを防ぐ主な手段になる）

## デプロイ

1日1回動くクラウドのスケジューラ（例: AWS EventBridge + Lambda）。秘密情報
（APIキー、Webhook URL、通知用トークン）は環境変数やシークレットマネージャー経由で
渡し、コミットはしません。[.env.example](../.env.example)を参照してください。
